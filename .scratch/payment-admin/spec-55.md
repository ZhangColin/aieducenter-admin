# Spec：payment BFF 契约对齐（金额 Long 分 / lifecycle 语义形状 / refundBacklog 嵌套 / ghost 字段清除）

（承 Agent Brief，决策依据 [ADR-0011](../blob/develop/docs/adr/0011-bff-amount-long-cents-and-verbatim-provider-mirror.md)；术语见 CONTEXT.md「支付管理上下文」「BFF 忠实透传 provider 契约」。）

## Problem Statement

运营人员在统一后台使用支付管理时：订单生命周期时间线**打不开**（后端反序列化直接报错——wire 预期的包装信封与 payment 实际返回的扁平事件数组根本对不上）；统计概览里退款待审核积压**恒为空**（字段名与嵌套形状双不符），积压金额更是无从谈起；订单/退款的金额字段类型是 BigDecimal 承整数分——类型撒谎，文档还错称"以元承"；退款列表声称有的审核人 ID / 审核时间两个字段从来都是 null。前端开发者拿到的北向契约是 admin"加了戏"的想象，与 payment 真实契约三层对不上。

## Solution

admin 作为 BFF **忠实按 payment 真实契约中转**（逐字镜像 payment 源码 Response/Query，零加戏）：lifecycle 改为 payment 的语义事件形状与真实信封，时间线恢复可用；金额全链 `Long`（分）、比率保持 `BigDecimal`；退款待审核积压以嵌套 `refundBacklog{pendingCount, pendingAmount}` 透传，积压金额首次可见；payment 从不发送的出口字段删掉；北向 Query 的审核人筛选保留（payment 支持）。前端（admin-web #54）按钉住的新形状联动。

## User Stories

1. As an 运营人员, I want 在订单详情抽屉打开生命周期时间线（不再报错）, so that 客诉排查时能看到"这单经历了什么"。
2. As an 运营人员, I want 每条生命周期事件显示动作中文名（`actionName`）、结果（`outcome`）、执行方（`performer`/`performerSystem`）与补充说明（`detail`）, so that 不查码表就能读懂时间线。
3. As an 运营人员, I want 时间线按事件时间排序、同刻以源记录 id 为稳定键, so that 还原真实先后顺序。
4. As an 运营人员, I want 生命周期事件区分来源（网关交互 `GATEWAY` / 行为者操作 `OPERATION`）, so that 一眼分清机器交互与人做的操作。
5. As an 运营人员, I want 统计概览显示退款待审核积压的**笔数和金额**（`refundBacklog.pendingCount` / `pendingAmount`）, so that 同时评估审核工作量和占压资金。
6. As an 运营人员, I want 订单/退款列表、详情及各统计端点的金额以分为单位的整数, so that 金额语义全程一致、无元/分歧义。
7. As an 运营人员, I want 按审核人筛选退款单, so that 定位某位审核员经手的退款（payment 支持该筛选，admin 保留）。
8. As an 运营人员, I want 退款列表不再出现恒为空的审核人 ID / 审核时间列, so that 界面字段都真实有据。
9. As a 前端开发者 (admin-web), I want 北向形状与 payment 同型（金额 Long、嵌套 backlog、语义事件）, so that typings 直接镜像后端契约、不再对着两套形状脑内换算。
10. As a 前端开发者, I want 金额以 JSON string 到达（框架 Long 防精度丢失）, so that 与 `auditorId` 等既有 Long 字段同一处理范式（入口统一转 Number）。
11. As a 前端开发者, I want 以 admin 契约测试钉住的 fixture 为对接权威, so that 前后端对契约的理解没有第二解释。
12. As a BFF 维护者, I want wire 镜像 DTO 与 payment 源码逐字一致, so that payment 侧变更时问题在反序列化层尽早暴露而非静默吞字段。
13. As a BFF 维护者, I want lifecycle 端点进入契约测试覆盖, so that 信封级偏差不再运行时才炸（本次正是零覆盖才漏网）。
14. As a BFF 维护者, I want 删掉 payment 不发送的出口字段、不新增 payment 实有而未暴露的字段, so that DTO 声称的字段集 = payment 实际提供的字段集（零加戏）。
15. As a BFF 维护者, I want 比率/均值字段（`successRate` 等）保持 `BigDecimal`、金额用 `Long`, so that 与 provider 的分型约定一致，不引入换算双逻辑。
16. As a BFF 维护者, I want 北向 Query 金额区间以分 Long 透传（前端已按分提交）, so that 筛选语义与 payment 完全一致。
17. As a 平台维护者, I want 本对齐决策（ADR-0011）成为横切规则被兄弟 BFF 子上下文（account 等）继承, so that 后续接入新服务不再重蹈"按文档加戏"覆辙。

## Implementation Decisions

- **逐字镜像 provider（ADR-0011 核心原则）**：wire 镜像 DTO、北向 Response、北向 Query 的字段名/类型/嵌套/信封/token 值一律照 payment 源码（`application/dto/response|query/*.java`），不增删、不重命名、不换形状、不顺手改善。写 wire 前先读兄弟仓 payment 源码，**不按 spec 文档**。
- **lifecycle 重写**：payment 实返 `ApiResponse<List<OrderLifecycleResponse>>`——**扁平事件数组**，无 orderNo 包装（orderNo 是路径参数）。事件为语义 9 字段 `(id, source, createdAt, action, actionName, outcome, performer, performerSystem, detail)`；`source` token 值 `GATEWAY`/`OPERATION`。admin wire 信封、北向 Response、应用层映射、客户端方法 typeres 全部按此重写；北向 404 翻译（订单不存在 → 404）行为保持。
- **金额全链 Long（分）**：payment 相关全部 wire record、北向 Response、北向 Query 的**金额**字段 `BigDecimal → Long`；订单详情、退款详情、6 个 stats 端点全覆盖。**比率/均值字段保持 `BigDecimal`**（`successRate`/`refundRate`/`approvalRate`/`avgAuditDurationMinutes`/`avgExecutionTimeMs`——payment 亦如此）。不做分↔元换算。
- **北向 JSON string 形态接受**：框架全局 Long→`ToStringSerializer`，金额在北向 JSON 为 string（`"9900"`）；不为"金额像数字"把 Long 包 BigDecimal 出 number。北向 Query javadoc「金额暂以元承」立场作废（事实契约一直是分）。
- **status-distribution**：扁平 `refundPendingAuditCount` → 嵌套 `refundBacklog{ pendingCount, pendingAmount }` 镜像；分桶 `count`/`amount` 对齐 Long。积压金额 `pendingAmount` 首次透出。
- **refund ghost 清除**：出口 wire + 北向 summary/detail 删 `auditorId`/`auditedAt`（payment 从不发送）；**北向 Query 的 `auditorId` 筛选保留**（payment `RefundOrderQuery` 支持）。**不**新增 payment 实有而未暴露的字段（`approvedAt`/`auditAgreed`/`auditRemark` 等）——展现需求联调后从 UI 起单向另提（ADR-0011 §4）。
- **payment 侧零改动**：已核实其契约干净（金额全 long 分、BigDecimal 仅比率）。
- **已完成不重做**：枚举 Integer code + `*Name`（#50 已落）；`payMode`/`accessType`/`paymentChannel` + 各 `*Name`（payment #21 已补齐暴露，admin wire 已有，保留）。
- **门禁 defer**：不做 OpenAPI 生成 / 跨仓契约门禁——provider 漂移等发现问题开新票重新对接。

## Testing Decisions

- **好测试只测外部行为**：从"payment 真实形状 JSON → 北向 Response record"整条 BFF 路径断言；不断言内部私有映射方法结构（重构不红）。
- **单一 seam**：复用既有传输替换脚手架（`PaymentWireTestSupport`——子类化 `OpenApiClient` 仅替换 HTTP 传输，真实 `PaymentClient` + 真实 typeres + 真实 Jackson 反序列化 + 真实 AppService 映射）。**不新建 seam**：三个既有契约测试类（列表信封 / stats 查询 / 枚举名透传）fixture 扩展新形状；lifecycle **新增**一个契约测试类挂同一 seam（当前零覆盖）。
- **fixture 取 payment 真实序列化形状**：Long/金额字段用 **string 形态**（`"amount": "9900"`——框架 `ToStringSerializer`，生产 `auditorId: string` 实证）；lifecycle fixture 用真实信封（`ApiResponse.data` 为**扁平数组**）。
- **Prior art**：`PaymentClientListEnvelopeContractTest` 的范式——信封不丢字段断言 + 枚举 code/`*Name` 透传断言；新测试同风格（`given_{条件}_when_{操作}_then_{预期}` 命名、AssertJ）。
- 北向 JSON 的 string 形态由"record 字段是 Long"+ 框架全局行为共同钉住，不为框架序列化单开 controller-slice seam。
